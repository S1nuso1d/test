# Product Copy AI

**Версия:** 0.9.2  
Локальный AI-помощник для подготовки черновиков карточек контрольно-измерительных приборов для B2B-интернет-магазина.

Приложение принимает сведения о товаре через веб-форму или JSON, передаёт текстовые задачи локальной LLM через Ollama и возвращает структурированную карточку. Технические характеристики переносятся из исходного JSON программно, чтобы модель не изменяла числовые параметры и единицы измерения.

## Возможности

Для каждого товара приложение формирует SEO-заголовок до 70 символов, SEO-описание 800–1200 символов, структурированные характеристики, 3–5 поисковых запросов и коммерческий блок для менеджера.

Дополнительно реализованы:

- веб-форма и JSON-режим;
- пакетная обработка до 10 товаров;
- импорт CSV/XLSX;
- извлечение текста из PDF-паспортов;
- экспорт JSON и Markdown, копирование отдельных полей;
- меню с несколькими готовыми примерами товаров и пакетами для быстрой проверки;
- проверки структуры, чисел, единиц измерения и части рискованных утверждений;
- повторные попытки генерации и отдельное исправление SEO-описания;
- отчёт о недостающих данных, предупреждениях и статусе карточки.

## Как пользоваться

### Веб-форма

Заполни название товара, производителя, категорию, описание и технические характеристики. Необязательные поля можно не указывать. Кнопка **«Загрузить пример»** открывает список готовых карточек: манометр DM 02, термопреобразователь ОВЕН, преобразователь давления ОВЕН, пару товаров из тестового задания или все три примера одним пакетом. При выборе одного товара данные появляются в форме; при выборе набора из нескольких товаров приложение переключается в JSON-режим и подставляет массив для пакетной генерации.

### JSON

Основные поля: name, manufacturer, category (необязательно), specs и description.

Пример:

~~~json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "category": "pressure_gauge",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления."
}
~~~

Категория помогает определить ожидаемые характеристики. Поддерживаются pressure_gauge, temperature_transmitter, pressure_transmitter, temperature_sensor, flow_meter и level_sensor. Если категорию не указать, приложение определяет её по названию и описанию.

### Пакетный режим и импорт

В JSON-режиме можно передать массив из 1–10 товаров. Обработка последовательная, чтобы не перегружать локальную модель.

Для импорта CSV/XLSX используется первая строка с заголовками. Шаблон находится в examples/catalog_import_template.csv. PDF-парсер извлекает текст и простые строки «Характеристика: значение». OCR для сканов не поддерживается, сложные таблицы могут извлекаться некорректно. После импорта обязательно сверь данные с паспортом.

Результат можно скопировать по отдельным полям или экспортировать в JSON и Markdown.

### Особенности исходных данных

- Для ДТС024 карточка указывает НСХ 100П и диапазон группы 50П/100П/Pt100 −50…+250 °C. Класс допуска указан несколькими вариантами (А, В, С), поэтому одно значение в JSON не выбрано.
- Для ПД100 краткий и подробный блоки карточки расходятся по присоединению к процессу (G 1/4 и M20×1,5) и сопротивлению нагрузки (0…1800 Ом и 0…1,0 кОм). Эти два поля исключены из JSON, чтобы не закреплять противоречивое значение как факт.
- Цена, наличие и срок поставки не включались: они динамические и не нужны для подготовки технической карточки.

### Проверка наличия в XML-фиде

В этой среде сам XML-фид скачать не удалось. Перед сдаваемой генерацией проверь наличие обеих моделей в выгрузке на своём компьютере:

~~~powershell
$feedPath = Join-Path $env:TEMP "souz_pribor_feed.xml"
Invoke-WebRequest -Uri "https://www.souz-pribor.ru/yml/any/feed.xml" -OutFile $feedPath
$feedText = Get-Content -Path $feedPath -Raw -Encoding UTF8

$names = @("ДТС024-100П.В3.30/1", "ПД100-ДИ4,0-185-0,5")
foreach ($name in $names) {
    [pscustomobject]@{
        Product = $name
        FoundInFeed = $feedText.Contains($name)
    }
}
~~~

Для обеих позиций должно быть FoundInFeed = True. Если какая-то позиция не найдена, замени её товаром, который присутствует в выгрузке.

### Реальная генерация перед сдачей

Сначала запусти FastAPI, затем во втором окне PowerShell выполни команду после проверки обеих позиций в XML:

~~~powershell
python scripts/run_submission_check.py --products examples/product_oven_dts024_100p_v3_30_1.json examples/product_oven_pd100_di4_0_185_0_5.json --confirm-assignment-products
~~~

Скрипт обращается к локальному API и сохраняет реальные ответы модели в examples/results/:

- JSON каждой карточки;
- Markdown каждой карточки;
- общий submission_report.md.

Проверяются длина SEO-полей, число поисковых запросов, коммерческий блок, перенос характеристик, замечания факт-аудита и использование резервного SEO-текста. Код возврата 2 или замечания в отчёте означают, что результат нужно исправить или проверить, а не отправлять как готовый.

## Архитектура и принятые решения

### Локальная Ollama вместо облачного API

Выбрана локальная модель: не нужен облачный API-ключ, исходные данные не требуется отправлять внешнему LLM-провайдеру. Компромисс — качество и скорость зависят от модели и компьютера.

### Python переносит характеристики, LLM пишет текст

Рассматривались два подхода: поручить LLM сформировать всю карточку или использовать её только для текстовых блоков. Выбран второй вариант. Технические характеристики формируются Python-кодом непосредственно из входного JSON. Это снижает риск изменения диапазона, единиц измерения и других технических значений.

### Структурированный ответ вместо свободного текста

Для ответа модели используется Pydantic-схема и структурированный JSON. Это упрощает валидацию обязательных полей, SEO-ограничений, запросов и коммерческого блока, а также экспорт.

### Повторные попытки и резервный текст

При нарушении требований модель получает конкретные замечания и предыдущий черновик: исправлять нужно проблемные фрагменты, сохраняя удачные части. Из трёх попыток выбирается вариант с наименьшим количеством ошибок. Для исправления SEO-описания предусмотрено до двух отдельных попыток. Если после повторов остаются неподтверждённые утверждения или несоответствия значений, приложение удаляет целые предложения и пункты, не переписывая и не дополняя факты. После такой очистки карточка обязательно получает статус needs_review. Если SEO-описание не проходит проверки длины или содержания, приложение пытается сократить его по границам предложений или собрать резервный вариант из исходных фактов. Резервный текст также помечается и требует редакторской проверки.

### Последовательная пакетная обработка

Пакет обрабатывается по одному товару. Параллельные запросы могли бы перегружать локальную модель и видеопамять, поэтому для прототипа выбрана последовательная обработка.

### Валидаторы — не доказательство достоверности

Проверяются формат, числовые значения с учётом знаков, в том числе словесные формы «минус/плюс», пары «число + единица», соответствие значений названиям характеристик и сохранность ограничителей «не более/не менее/до/от». Для поисковых запросов допускается отсутствие единицы измерения, но явная подмена единицы отклоняется. Обозначения напряжения распознаются с учётом регистра. Температурные диапазоны измеряемой среды и окружающего воздуха сопоставляются раздельно; токовый выход считается заполненным полем «Выходной сигнал». Факт-аудит отмечает неподтверждённые свойства и рекламные обещания, сопоставляет формулировки с исходными данными и очищает неподтверждённые предложения после исчерпания повторных попыток; он не считает нейтральный вопрос к поставщику утверждением о товаре. Длинное SEO сокращается только целыми предложениями и повторно проходит проверки. Это эвристики, а не полноценная проверка каждого предложения по паспорту. Поэтому карточка остаётся черновиком и требует редакторской проверки.

## Ограничения и дальнейшие улучшения

- Факт-аудит и проверка чисел/единиц эвристические и не гарантируют обнаружения всех смысловых галлюцинаций.
- Отсутствие предупреждений не доказывает достоверность текста.
- Категорийные списки ожидаемых характеристик нужно согласовывать с каталогами производителей.
- PDF-парсер не поддерживает OCR; сканы и сложные таблицы требуют отдельной обработки.
- Поисковые запросы не сверяются с реальной статистикой поискового спроса.
- Сервис создаёт черновики и не публикует карточки автоматически.
- Нет базы данных, авторизации, истории генераций и полноценной CMS.
- Пакетная обработка последовательная.

Дальнейшие улучшения: экспертный набор эталонных карточек, проверка утверждений с привязкой к источникам, OCR и улучшение извлечения таблиц из паспортов.
