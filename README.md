# Product Copy AI v0.9.2

Локальный AI-помощник для подготовки черновиков карточек контрольно-измерительных приборов для B2B-интернет-магазина. Основа приложения — FastAPI и Ollama; облачный API-ключ не требуется.

## Возможности

Версия 0.9.2 добавляет воспроизводимую проверку готовности к сдаче на реальной локальной модели. Версия 0.9.1 исправляет распознавание названий характеристик с учётом границ слов и падежных форм, точнее проверяет диапазоны значений и не допускает технические параметры в поле целевой аудитории.


- Ввод товара через простую веб-форму, расширенный JSON-режим и пакетную обработку до 10 товаров.
- Локальная генерация через Ollama Python SDK и структурированный JSON Schema output.
- SEO-заголовок до 70 символов, SEO-описание 800–1200 символов, 3–5 уникальных поисковых запросов и структурированный коммерческий блок.
- Технические характеристики копируются приложением непосредственно из входного JSON; LLM их не переписывает.
- До трёх попыток генерации полной карточки с передачей модели конкретных ошибок проверки.
- Две отдельные попытки целевого исправления SEO-описания; при неудаче — резервный локальный шаблон из исходных фактов и рекомендаций покупателю.
- Формальная оценка 0–100 по длине и структуре полей; она не является оценкой смысловой достоверности. При использовании SEO-шаблона результат всегда получает статус `needs_review`.
- После неудачных попыток лучший черновик возвращается со статусом `needs_review`, списком нарушений и предупреждением. Резервный SEO-шаблон также всегда требует ручной проверки и не выдаётся за полноценный текст модели.
- Проверка числовых значений и пар «число + единица измерения» во всех генерируемых текстовых полях: заголовке, описании, запросах и коммерческом блоке. Например, подмена `1,6 МПа` на `1,6 бар` выявляется даже при совпадении числа.
- Сопоставление значений рядом с названиями характеристик: система проверяет типовые параметры, учитывает падежные формы названий и ловит подмены вроде `100 мм` → `200 мм`, `IP65` → `IP54` и сокращение диапазона `0–1,6 МПа` до `до 1,6 МПа`. Диапазоны температуры, расхода и измерений распознаются раздельно.
- Импорт до 10 товаров из CSV/XLSX с русскими и английскими заголовками; некорректные строки перечисляются отдельно.
- Извлечение текста из PDF-паспорта и первичное заполнение карточки по строкам «Характеристика: значение». Извлечённые поля всегда нужно сверить с оригиналом.
- Эвристический аудит рискованных утверждений о материале корпуса, IP-защите, влагозащите, взрывозащите, сертификации, поверке, беспроводной связи, дисплее, санитарном исполнении, стойкости к среде и гарантии. Найденные утверждения показываются отдельно и переводят карточку в `needs_review`.
- Ограничения на длину полей, число характеристик и общий размер входного товара для защиты от чрезмерно больших запросов к локальной модели.
- Определение недостающих характеристик по категории прибора (манометр, преобразователь температуры/давления, датчик температуры, расходомер, датчик уровня). Неизвестная категория не получает случайный универсальный список требований.
- Отчёт о пустых полях, пустых характеристиках и ожидаемых, но не указанных параметрах.
- Адаптивный интерфейс с отдельными режимами формы и JSON, динамическими строками характеристик, компактным статусом модели и понятной индикацией генерации.
- Просмотр результата по разделам, копирование отдельных полей, экспорт в JSON и Markdown; пакетный экспорт.
- Обработка ошибок подключения, отсутствующей модели, неверного JSON и недостатка исходных данных.

## Требования

- Python 3.11 или новее.
- Установленный и запущенный [Ollama](https://ollama.com/download).
- Загруженная модель. По умолчанию используется `qwen3.5:9b`.

## Установка на Windows

```powershell
ollama list
ollama pull qwen3.5:9b

py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -e ".[dev]"
Copy-Item .env.example .env
```

При необходимости отредактируйте `.env`:

```dotenv
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen3.5:9b
OLLAMA_TIMEOUT_SECONDS=300
OLLAMA_NUM_CTX=8192
OLLAMA_NUM_PREDICT=2200
OLLAMA_KEEP_ALIVE=5m
```

Файл `.env` исключён из Git. Для локального Ollama API-ключ не нужен.

## REST API

- `POST /api/generate` — один товар.
- `POST /api/generate/batch` — пакет до 10 товаров; обработка последовательная, чтобы не перегружать локальную модель.
- `POST /api/test-connection` — тестовый запрос к модели.
- `GET /api/models` — список установленных локальных моделей Ollama.
- `POST /api/benchmark` — последовательное сравнение 2–3 установленных моделей на одном товаре с замером времени и формальных метрик.
- `POST /api/export/markdown` — преобразование результата генерации в Markdown.
- `POST /api/import/catalog` — импорт до 10 товаров из CSV/XLSX (столбец `Название` обязателен; остальные неизвестные столбцы становятся характеристиками).
- `POST /api/import/passport` — извлечение текста и простых пар «параметр: значение» из PDF-паспорта.

В товар можно добавить необязательное поле `category`, например `pressure_gauge`, `temperature_transmitter`, `pressure_transmitter`, `temperature_sensor`, `flow_meter` или `level_sensor`. Если поле не указано, приложение пытается определить категорию по названию и описанию. Для неизвестной категории специфические характеристики не навязываются.

Пример входных данных:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "category": "pressure_gauge",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Это пример из иллюстрации тестового задания, а не полный паспорт реального товара.

## Второй демонстрационный товар

Для проверки второго типа прибора добавлен внешний демонстрационный набор [ОВЕН ПД100И](examples/product_owen_pd100i_external_demo.json). Его характеристики собраны из [официального руководства производителя](https://docs.owen.ru/product/pd100i/176); принята конфигурация ДИ, модель 1Х1, диапазон 0–1,6 МПа. Неподтверждённые для конкретного экземпляра точность и присоединение намеренно оставлены незаполненными. Обоснование каждого выбранного поля и ограничения набора описаны в [источнике данных](examples/sources/owen_pd100i.md).

**Важно:** это реальный внешний демонстрационный пример, но не второй товар из материалов работодателя. Он позволяет проверить генерацию по второму товару, однако не закрывает требование задания о двух товарах работодателя. Не представляй его как полученные от работодателя данные.

Проверить оба примера на локальной Ollama:

```powershell
python scripts/run_submission_check.py --products examples/product_dm_02.json examples/product_owen_pd100i_external_demo.json
```

Отчёт сгенерирует две карточки и явно оставит подтверждение источника задания незакрытым. Флаг `--confirm-assignment-products` допустим только тогда, когда оба переданных JSON действительно содержат товары из материалов работодателя.

## Импорт каталога и паспортов

Для CSV/XLSX используй первую строку как заголовки. Поддерживаются поля на русском и английском: «Название» / `name`, «Производитель» / `manufacturer`, «Категория» / `category`, «Описание» / `description`. Остальные столбцы импортируются как технические характеристики. Пример находится в `examples/catalog_import_template.csv`. За один импорт обрабатываются первые 10 товаров; строки без названия пропускаются и попадают в список ошибок.

PDF-паспорт должен содержать извлекаемый текст. Приложение извлекает до 30 страниц и пытается разобрать простые строки вида «Диапазон измерений: 0–1,6 МПа». Для отсканированных изображений OCR не поддерживается. Автоматически извлечённые значения нужно проверить по исходному документу до генерации карточки. Максимальный размер загружаемого файла — 8 МБ.

## Статусы ответа

- `generated` — форматные проверки пройдены; карточка всё равно остаётся черновиком и требует редакторской проверки.
- `needs_review` — остались ошибки формальной проверки или использован резервный SEO-шаблон. Черновик и замечания возвращаются пользователю; публикация без редакторской проверки не допускается.
- `needs_data` — исходной информации недостаточно даже для осмысленного запроса к LLM.

## Проверка

```powershell
python -m pytest -q
```

Тесты проверяют категорийные шаблоны недостающих характеристик, перенос исходных значений, ограничения SEO-полей, контроль чисел, единиц и значений рядом с названиями параметров с учётом падежных форм, сохранение обеих границ диапазонов, разделение диапазонов температуры и измерений, структуру поля «Кому подходит», безопасную сериализацию пользовательского JSON, CSV/XLSX-импорт, извлечение текстовых PDF-паспортов, лимиты входных данных, повторные попытки и сравнение моделей через API. Тесты не требуют реального подключения к Ollama: SDK изолирован моками. Качество текста и скорость необходимо дополнительно проверить на локальной модели. GitHub Actions выполняет `ruff check` и `pytest` при каждом push и pull request.

## Промпт и защита от недостоверных сведений

Системный промпт запрещает придумывать технические характеристики, конвертировать единицы и выполнять инструкции, попавшие в название или описание товара. Исходный JSON помещается в отдельный блок `<product_data>` и трактуется как недоверенные данные.

Технические характеристики в ответе формирует Python-код напрямую из исходного JSON. LLM отвечает за SEO-текст, поисковые запросы и коммерческий блок. Локальный валидатор проверяет длину полей, число запросов, новые числовые токены и сочетания чисел с единицами измерения во всех сгенерированных текстовых полях. При ошибках приложение передаёт модели конкретный список замечаний и повторяет генерацию до трёх раз. Если SEO-описание не проходит проверку длины или чисел/единиц измерения, запускаются до двух отдельных попыток исправления только этого поля. Если они не помогают, используется детерминированный резервный текст из исходных характеристик и нейтральных рекомендаций по проверке перед покупкой. Такой режим отмечается отдельным признаком `seo_fallback_used` и статусом `needs_review`.

Проверка чисел и единиц — только эвристика. Она не выявляет все смысловые галлюцинации: например, неподтверждённое утверждение без чисел может пройти, а контекстная связь параметра с конкретным свойством требует проверки по паспорту. JSON Schema подтверждает структуру, а не фактическую достоверность. Результат обязательно должен проверяться человеком перед публикацией.

Формальная оценка качества в ответе — это сумма проверок заголовка, длины описания, количества запросов, заполненности коммерческого блока и числового контроля. Она не измеряет семантическую точность и не должна трактоваться как вероятность отсутствия галлюцинаций.

## Ограничения и дальнейшие улучшения

- Категорийные шаблоны характеристик эвристические; их нужно согласовать с каталогом конкретного производителя и типами приборов.
- Проверка чисел, единиц измерения и выбранных рискованных утверждений снижает часть ошибок, но не является полной семантической проверкой. Правила не охватывают все возможные формулировки, могут давать ложные срабатывания и не доказывают достоверность текста без замечаний. Сопоставление значений по атрибутам — ограниченный набор правил для типовых характеристик, а не полная семантическая верификация.
- Нет базы данных, авторизации, истории генераций, CMS и публикации карточек.
- Пакетная обработка выполняется последовательно; параллельный режим не включён, чтобы не перегружать локальную модель.
- Поисковые запросы генерируются LLM и не подтверждаются реальными объёмами поиска.
- Сравнение моделей измеряет полное время генерации в приложении, включая повторные попытки и исправление SEO; первый запуск может включать загрузку модели в память, поэтому для точного сравнения стоит повторить тест дважды и учитывать второй прогон.
- Для следующего этапа можно добавить сопоставление каждого утверждения с источником, извлечение сведений из PDF-паспортов, каталог утверждённых терминов и golden dataset с экспертно проверенными карточками.

## Проверка перед сдачей на реальной модели

Для подготовки проверяемых примеров запусти приложение и выполни скрипт:

```powershell
python scripts/run_submission_check.py --products examples/product_dm_02.json C:\path\to\second_product.json
```

Скрипт вызывает локальный API, сохраняет реальные ответы в `examples/results/` (JSON и Markdown), а также формирует `submission_report.md`. Он проверяет ограничения SEO, число запросов, структуру коммерческого блока, точный перенос характеристик, наличие замечаний факт-аудита и использование резервного SEO-шаблона. Код не генерирует фиктивные примеры. Если передан только один товар, отчёт явно фиксирует, что требование о двух примерах не закрыто.

Полный чек-лист и пояснение решений находятся в [docs/SUBMISSION_CHECKLIST.md](docs/SUBMISSION_CHECKLIST.md). Даже при успешном автоматическом отчёте карточки остаются черновиками и требуют ручной сверки с исходными документами.
Дополнительно: [сценарий демонстрации](docs/DEMO_SCRIPT.md) и [позиционирование и отличия продукта](docs/PRODUCT_POSITIONING.md). Черновик сопроводительного сообщения — [docs/SUBMISSION_MESSAGE.md](docs/SUBMISSION_MESSAGE.md).


## Выполнение тестового задания

В приложенном к задаче PDF приведён пример одного товара — манометра DM 02. Несмотря на упоминание двух товаров, полные исходные данные второго товара в PDF отсутствуют. В `examples/product_demo_temperature_transmitter_synthetic.json` и `examples/demo_batch_synthetic.json` добавлен синтетический прибор только для демонстрации пакетного режима; он не является товаром из задания. Перед финальной сдачей нужно запросить второй набор данных у работодателя, заменить синтетическую запись реальными сведениями и сохранить фактические результаты генерации для обоих товаров.
