# Product Copy AI v0.9.2

Локальный AI-помощник для подготовки черновиков карточек контрольно-измерительных приборов для B2B-интернет-магазина. Приложение построено на Python и FastAPI, а генерация выполняется локальной моделью через Ollama. Облачный API-ключ не требуется.

## Что делает приложение

Product Copy AI принимает сведения о товаре и формирует черновик карточки, который контент-менеджер может проверить, отредактировать и скопировать в каталог.

Для каждого товара приложение формирует:

- SEO-заголовок — не более 70 символов;
- SEO-описание — 800–1200 символов;
- структурированный перечень технических характеристик;
- 3–5 поисковых запросов;
- коммерческий блок: целевая аудитория, решаемые задачи и тезисы для менеджера;
- информацию о недостающих данных, замечаниях и статусе проверки.

## Основные возможности

- Ввод товара через веб-форму или JSON; пакетная обработка до 10 товаров.
- Локальная генерация через Ollama Python SDK и структурированный ответ по JSON Schema.
- До трёх попыток генерации с передачей модели конкретных замечаний валидатора.
- До двух отдельных попыток исправления SEO-описания. Если они не помогают, приложение может сформировать резервный текст из исходных фактов и нейтральных рекомендаций; такой текст помечается как резервный и требует ручной проверки.
- Технические характеристики переносятся Python-кодом непосредственно из исходного JSON, а не генерируются моделью.
- Проверка длины SEO-полей, количества поисковых запросов, структуры коммерческого блока, чисел и сочетаний «значение + единица измерения».
- Сопоставление части значений с названиями характеристик: например, система проверяет типовые подмены диапазона, класса точности, диаметра и степени защиты.
- Эвристический аудит рискованных утверждений о материале корпуса, IP-защите, влагозащите, взрывозащите, сертификации, поверке, беспроводной связи и других свойствах, которые нельзя автоматически приписывать прибору без источника.
- Определение ожидаемых, но отсутствующих характеристик для поддерживаемых категорий приборов.
- Импорт до 10 товаров из CSV/XLSX.
- Извлечение текста и простых пар «параметр: значение» из текстовых PDF-паспортов.
- Экспорт результата в JSON и Markdown, копирование отдельных полей и пакетный экспорт.
- Последовательное сравнение 2–3 установленных моделей Ollama на одном товаре.
- Адаптивный веб-интерфейс и REST API.

## Технологии и требования

- Python 3.11+
- FastAPI, Uvicorn, Pydantic
- Ollama и локальная LLM
- Jinja2, HTTPX
- OpenPyXL для XLSX, pypdf для текстовых PDF
- Pytest и Ruff для тестирования и линтинга

Необходимо установить и запустить [Ollama](https://ollama.com/download), а также загрузить модель. По умолчанию используется `qwen3.5:9b`.

## Установка и запуск на Windows

Откройте PowerShell в корневой папке репозитория:

```powershell
ollama pull qwen3.5:9b

py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"

Copy-Item .env.example .env
```

При необходимости измените параметры в `.env`:

```dotenv
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen3.5:9b
OLLAMA_TIMEOUT_SECONDS=300
OLLAMA_NUM_CTX=8192
OLLAMA_NUM_PREDICT=2200
OLLAMA_KEEP_ALIVE=5m
```

Файл `.env` исключён из Git. Для локального экземпляра Ollama API-ключ не нужен.

Запустите сервер:

```powershell
uvicorn app.main:app --reload
```

Адреса после запуска:

- Веб-интерфейс: http://127.0.0.1:8000/
- Swagger UI: http://127.0.0.1:8000/docs
- Проверка работоспособности: http://127.0.0.1:8000/health
- Статус локальной модели: http://127.0.0.1:8000/api/status

В интерфейсе нажмите «Проверить модель», затем введите товар через форму или JSON. Для пакетной обработки можно передать массив из 1–10 товаров.

## Формат входных данных

Пример JSON для манометра DM 02:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "category": "pressure_gauge",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Поле `category` необязательно. Среди поддерживаемых категорий: `pressure_gauge`, `temperature_transmitter`, `pressure_transmitter`, `temperature_sensor`, `flow_meter`, `level_sensor`. Если категория не указана, приложение пытается определить её по названию и описанию. Для неизвестной категории случайный список обязательных характеристик не применяется.

Пример DM 02 основан на иллюстрации из тестового задания и не является полным паспортом конкретного изделия.

## REST API

- `POST /api/generate` — генерация карточки одного товара.
- `POST /api/generate/batch` — последовательная пакетная генерация до 10 товаров.
- `POST /api/test-connection` — проверка соединения с Ollama.
- `GET /api/models` — список локальных моделей.
- `POST /api/benchmark` — последовательное сравнение 2–3 локальных моделей.
- `POST /api/export/markdown` — экспорт результата в Markdown.
- `POST /api/import/catalog` — импорт CSV/XLSX.
- `POST /api/import/passport` — извлечение текста из PDF-паспорта.

## Контроль достоверности и статусы

Входные данные товара рассматриваются как данные, а не как инструкции для модели. Системный промпт запрещает придумывать характеристики, менять единицы измерения и выполнять команды, случайно попавшие в название или описание товара.

Python формирует список технических характеристик из исходного JSON. LLM используется для SEO-текста, поисковых запросов и коммерческого блока. После генерации локальные проверки анализируют формальные ограничения и часть возможных расхождений. При обнаружении проблем модель получает конкретные замечания и может повторить генерацию.

Статусы результата:

- `generated` — предусмотренные формальные проверки пройдены. Это всё ещё черновик, который должен проверить человек.
- `needs_review` — остались замечания проверки либо использован резервный SEO-шаблон. Результат возвращается с предупреждениями, но не считается готовым к публикации.
- `needs_data` — исходной информации недостаточно для осмысленной генерации.

Формальная оценка `quality_score` отражает выполнение структурных требований. Она не является вероятностью достоверности и не заменяет редакторскую проверку.

## Импорт каталога и PDF-паспортов

Для CSV/XLSX используй первую строку как заголовки. Поддерживаются русские и английские названия столбцов: «Название» / `name`, «Производитель» / `manufacturer`, «Категория» / `category`, «Описание» / `description`. Остальные столбцы импортируются как характеристики. Шаблон: `examples/catalog_import_template.csv`.

PDF-парсер извлекает текст и пытается распознать простые строки вида «Диапазон измерений: 0–1,6 МПа». OCR для сканов не реализован; сложные таблицы могут быть извлечены некорректно. Любые автоматически заполненные значения необходимо сверить с оригинальным паспортом.

## Проверка проекта

Установи dev-зависимости и запусти:

```powershell
ruff check app tests scripts
python -m pytest -q
```

GitHub Actions запускает Ruff и pytest при push в `main` и при pull request. Тесты изолируют Ollama SDK моками: они проверяют логику приложения, но не оценивают качество текста, скорость и фактическое поведение каждой локальной модели. Для этого предусмотрен отдельный запуск на реальной Ollama.

## Два товара для тестового задания

В сообщении работодателя указано, что можно выбрать любые два товара из YML-фида СОЮЗ-ПРИБОР. В качестве входных данных подготовлены две разные категории:

- [ОВЕН ДТС024-100П.В3.30/1](examples/product_oven_dts024_100p_v3_30_1.json) — термопреобразователь сопротивления.
- [ОВЕН ПД100-ДИ4,0-185-0,5](examples/product_oven_pd100_di4_0_185_0_5.json) — преобразователь давления в полевом корпусе.

Источники карточек, выбранные характеристики и противоречия в исходных сведениях описаны в [docs/PRODUCT_SOURCES.md](docs/PRODUCT_SOURCES.md). У ПД100 противоречат друг другу данные карточки о присоединении к процессу и сопротивлении нагрузки; эти поля не перенесены во входной JSON без уточнения. Для ДТС024 класс допуска указан как несколько вариантов, поэтому одно значение не было выбрано произвольно.

Перед генерацией скачай фид и проверь наличие обеих моделей:

```powershell
$feedPath = Join-Path $env:TEMP "souz_pribor_feed.xml"
Invoke-WebRequest -Uri "https://www.souz-pribor.ru/yml/any/feed.xml" -OutFile $feedPath
Select-String -Path $feedPath -SimpleMatch -Pattern "ДТС024-100П.В3.30/1", "ПД100-ДИ4,0-185-0,5"
```

Если оба наименования присутствуют, запусти приложение и в другом окне PowerShell выполни:

```powershell
python scripts/run_submission_check.py --products examples/product_oven_dts024_100p_v3_30_1.json examples/product_oven_pd100_di4_0_185_0_5.json --confirm-assignment-products
```

Скрипт вызывает локальный API и записывает настоящие ответы LLM в `examples/results/`: два JSON, две Markdown-карточки и `submission_report.md`. Он проверяет SEO-ограничения, структуру коммерческого блока, перенос исходных характеристик, факт-аудит и использование резервного SEO-текста. Флаг `--confirm-assignment-products` используй только после проверки обеих моделей в фиде.

В репозитории также сохранён внешний демонстрационный пример [ОВЕН ПД100И-1Х1-EXI](examples/product_owen_pd100i_external_demo.json), собранный из документации производителя. Он не нужен для выполнения задания и не входит в выбранную пару.

## Принятые решения и ограничения

- Локальная Ollama выбрана для работы без облачного API-ключа и передачи товарных данных внешнему LLM-провайдеру.
- Технические характеристики переносятся из входных данных программно, чтобы снизить риск их изменения моделью.
- Ограниченные повторные попытки позволяют исправлять формальные нарушения, но не гарантируют смысловую точность каждой фразы.
- Аудит утверждений и проверка значений эвристические: неподтверждённое утверждение без числа или неизвестная формулировка могут пройти проверку. Отсутствие замечаний не доказывает достоверность карточки.
- Категорийные шаблоны ожидаемых характеристик нужно согласовывать с конкретными типами приборов и каталогом производителя.
- Поисковые запросы генерируются моделью и не подтверждаются фактическими объёмами поиска.
- PDF-парсер не использует OCR.
- В прототипе нет базы данных, авторизации, CMS, публикации карточек и серверного развёртывания.
- Пакетная генерация выполняется последовательно, чтобы не перегружать локальную модель.
