## 3. Ограничение исходного PDF

PDF говорит, что кандидату предоставляются данные по двум товарам, но в самом документе приведён только один пример JSON — манометр DM 02. Второго полного набора исходных данных в загруженном PDF нет. Проверены доступные вложения и файлы Library: найденные копии задания содержат тот же пример, отдельного набора второго товара среди найденных материалов нет.

Синтетический TP-200 в репозитории нужен только для демонстрации пакетного режима. Его нельзя выдавать за второй товар из задания. Если работодатель отправлял второй товар отдельным файлом или сообщением, нужно использовать именно его. Если нет — отправить вопрос о недостающих исходных данных; в репозитории подготовлен черновик сообщения `docs/SUBMISSION_MESSAGE.md`.

## 4. Как сформировать доказательства реальной генерации

1. Установить зависимости и запустить Ollama согласно README.
2. Запустить веб-приложение.
3. Передать два реальных JSON-файла скрипту `scripts/run_submission_check.py`.
4. Проверить `examples/results/submission_report.md`, оба JSON и оба Markdown-файла.
5. Вручную сверить факты с исходными данными и паспортом. Не отправлять результат, если появился резервный SEO-шаблон, `needs_review`, неподтверждённые утверждения или формальные нарушения.

Команда PowerShell:

```powershell
python scripts/run_submission_check.py --products examples/product_dm_02.json C:\path\to\second_product.json
```

Скрипт сохраняет настоящие ответы локальной LLM. Если передан только один товар, отчёт явно фиксирует, что комплект из двух примеров не закрыт.

## 5. Промпт и архитектурные решения

- Python/FastAPI выступает API-слоем и валидирует входные и выходные структуры.
- Ollama используется как локальный LLM-провайдер; облачный API-ключ не требуется.
- Pydantic-схемы задают ожидаемую структуру ответа.
- Системный промпт отделяет недоверенные данные товара от инструкций, запрещает выдумывать характеристики и требует сохранять границы диапазонов.
- Python переносит технические характеристики непосредственно из входа, а не поручает модели переписывать числовые значения.
- После генерации выполняются проверки длины, количества запросов, чисел/единиц, рискованных утверждений и части значений рядом с названиями параметров.
- При замечаниях система делает ограниченные повторные попытки; резервный SEO-текст маркируется и не считается полноценным текстом LLM.
- CSV/XLSX и текстовые PDF-паспорта импортируются эвристически; все извлечённые поля требуют сверки.

## 6. Ограничения, которые нужно честно раскрывать

- Эвристическая проверка не доказывает семантическую достоверность каждой фразы и может пропустить ошибку без числа или известного шаблона.
- Текст PDF извлекается без OCR; сканы и сложные таблицы могут не обработаться.
- Результаты и скорость зависят от локальной модели, её версии и настроек Ollama.
- Формальный `quality_score` оценивает структурные ограничения, а не вероятность достоверности.
- Поисковые запросы не проверяются по фактическим объёмам поиска.
- Сервис создаёт черновик, а не публикует карточку и не заменяет редактора.
- Полный проект и новая утилита должны быть проверены локально; наличие автоматических тестов не заменяет реальную проверку качества генерации.

## 7. Финальная редакторская проверка

Даже когда автоматический отчёт проходит без замечаний, проверь вручную каждое числовое значение и единицу, назначение прибора, коммерческие утверждения, естественность SEO-текста и отсутствие рекомендаций, ошибочно представленных как свойства товара. В сдаче приложи только результаты для реальных входных данных.
