# Чек-лист сдачи тестового задания

Этот документ отделяет требования задания от дополнительных возможностей прототипа. Он не заменяет проверку реальной генерации на установленной локальной модели.

## Обязательные требования из задания

- [ ] Приложение запускается по инструкции из README.
- [ ] Принимает JSON и данные через веб-форму.
- [ ] Отправляет данные в выбранную LLM; секреты не хранятся в коде.
- [ ] Формирует SEO-заголовок до 70 символов.
- [ ] Формирует SEO-описание длиной 800–1200 символов.
- [ ] Возвращает структурированные характеристики.
- [ ] Возвращает 3–5 поисковых запросов.
- [ ] Возвращает коммерческий блок: аудитория и задачи.
- [ ] Сообщает о недостающих данных.
- [ ] Обрабатывает неверный JSON, пустые поля и ошибки модели.
- [ ] Репозиторий содержит README с установкой и запуском.
- [ ] Для двух предоставленных товаров сохранены реальные результаты генерации.
- [ ] Описаны использованные промпты, решения, ограничения и возможные улучшения.

## Фактическое ограничение исходных материалов

В предоставленном PDF есть пример входных данных манометра DM 02, но нет второго полного набора данных. В репозитории есть синтетический TP-200 только для демонстрации пакетного режима. Его нельзя выдавать за второй товар из задания. Перед финальной сдачей нужно добавить второй реальный JSON, полученный от работодателя, и заново выполнить генерацию.

## Как сформировать проверяемые результаты

1. Установить зависимости и запустить Ollama согласно README.
2. Запустить веб-приложение.
3. Передать два реальных JSON-файла товаров скрипту `scripts/run_submission_check.py`.
4. Проверить `examples/results/submission_report.md`, оба JSON и оба Markdown-файла.
5. Вручную сверить факты с исходными данными и паспортом. Не отправлять результат, если появился резервный SEO-шаблон, `needs_review`, неподтверждённые утверждения или формальные нарушения.

Команда PowerShell:

```powershell
python scripts/run_submission_check.py --products examples/product_dm_02.json C:\path\to\second_product.json
```

Скрипт сохраняет настоящие ответы локальной LLM. Он не генерирует подставные примеры. При наличии только одного входного товара отчёт прямо укажет, что комплект из двух примеров не закрыт.

## Промпт и архитектурные решения

- Python/FastAPI выступает API-слоем и валидирует входные и выходные структуры.
- Ollama используется как локальный LLM-провайдер; ключ облачного API не требуется.
- Pydantic-схемы задают ожидаемую структуру ответа.
- Системный промпт отделяет недоверенные данные товара от инструкций, запрещает выдумывать характеристики и требует сохранять границы диапазонов.
- Python переносит технические характеристики непосредственно из входа, а не поручает модели переписывать числовые значения.
- После генерации выполняются проверки длины, количества запросов, чисел/единиц, рискованных утверждений и соответствия значений рядом с названиями параметров.
- При замечаниях система делает ограниченные повторные попытки; резервный SEO-текст маркируется и не считается полноценным текстом LLM.
- CSV/XLSX и текстовые PDF-паспорта импортируются эвристически; все извлечённые поля требуют сверки.

## Ограничения, которые нужно честно раскрывать

- Эвристическая проверка не доказывает семантическую достоверность каждой фразы и может пропустить ошибку без числа или известного шаблона.
- Текст PDF извлекается без OCR; сканы и сложные таблицы могут не обработаться.
- Результаты и скорость зависят от локальной модели, её версии и настроек Ollama.
- Формальный `quality_score` оценивает структурные ограничения, а не вероятность отсутствия галлюцинаций.
- Поисковые запросы не проверяются по фактическим объёмам поиска.
- Сервис создаёт черновик, а не публикует карточку и не заменяет редактора.

## Финальная редакторская проверка

Даже когда автоматический отчёт проходит без замечаний, проверить вручную: каждое числовое значение и единицу; назначение прибора; коммерческие утверждения; естественность SEO-текста; отсутствие рекомендаций, ошибочно представленных как свойства товара. В сдаче приложить только результаты для реальных входных данных.
